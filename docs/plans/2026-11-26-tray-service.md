## Decisions (user, 2026-11-26)
- SCM Windows Service (LocalSystem) supervises one **HTTP MCP** and applies updates; a per-user WPF tray app starts at login. The service stays, despite two reviewers calling it avoidable; Spike A (below) re-prices it before unit 3.
- One HTTP MCP instance serves every IDE and chat client (`AiDevHelpers.MCP.Http`, streamable HTTP). The stdio exe stays for clients that need it.
- UI: plain WPF on .NET 10, built-in Fluent theme (`ThemeMode`); tray icon via `H.NotifyIcon.Wpf`. Syncfusion dropped.
- MVVM: System.Reactive + CommunityToolkit.Mvvm; every page binds to view-model properties fed by `IObservable<T>`.
- Pages: Status (system status icon), IDE Instances (IDE, repo, file path), Config, Services (install/reinstall/etc., extensions, run-at-login, updates), Logs, About.
- Updater ported from VideoForensics: one staging folder, sources are a debug stage script and a GitHub release package.
- Dangerous tools over HTTP (`terminal_session`, `script_run`, `run_elevated_script`, `ide_kill_*`, process kill) require a **tray confirmation per call**; stdio is unchanged.

## Simplifications from review (applied)
- **No Host pipe.** The tray reads service state from SCM (`ServiceController`), MCP health/status/versions from the HTTP MCP (`/healthz` plus a status stream, bearer token), and elevates through pinned UAC scripts. This removes `Host.Contracts`, the pipe protocol, the pipe ACL and caller-SID work, and the Host-as-relay.
- **Instances and config are read in the tray** (user context): manifests in `%ProgramData%\AiDevHelpers\vs-instances`, `GitWorktree.RootFor/BranchFor` for repo, `ConfigHelper` for config. The SYSTEM service never opens a manifest path (red team: junction/UNC/NTLM/OOM). The tray treats manifests as untrusted input: 64 KB cap, depth limit, local-drive paths only, reparse points rejected, pid verified against the process list with start time (dead PIDs filtered, never deleted; not `VsInstanceRegistry.ListRunning`).
- **The service does exactly two things:** launch/supervise MCP.Http in the console user's session (`UserSession`), and apply signed updates. Target session is always the **console session**; second logged-on users get no MCP (documented, tested).

## HTTP MCP design
- `ModelContextProtocol.AspNetCore` matching Core's 2.4.0 (confirm on NuGet). **Stateful** sessions with idle timeout (stateless breaks `ControlSession`, log notifications, `McpServer` parameters in `TestingTools.LiveTestStart`/`LocalizationTools`). Sessions do not survive a restart; clients re-initialize (not all do; documented).
- Decided 2026-11-27: no bearer token. The listener is bound to `127.0.0.1`, so a token guarded nothing; loopback requests need no auth. Remaining controls: validate `Host` and `Origin`; no CORS. (The original text below required `Authorization`; superseded.)
- Bind `127.0.0.1`, fixed default port (configurable); validate `Host` and `Origin`; no CORS; `Authorization` required (blocks browser fetch via refused preflight). Bearer token generated at first run, `FixedTimeEquals`, minimum length, stored in a user-only-ACL file separate from the endpoint record (pid + port). The tray verifies the listener pid (`GetExtendedTcpTable`) before sending the token, defeating port squatting. Port conflict: loud `/healthz` cause, optional fallback port via the endpoint record. Rotation: tray rotates, process reloads without restart. Docs prefer env-var or `headersHelper` references over pasted tokens. Honest limit documented: the token is not a boundary against code already running as the user; the per-call confirmation is the real control.
- **Tray confirmation channel:** MCP.Http requests approval over a user-session pipe where the **tray is the server** (first-instance flag, user-only ACL). Authentication is mutual: MCP verifies the server pid is the tray exe; the tray verifies the client pid is the MCP.Http exe (image-path checks are weak against same-user spoofing; documented limit). Each request carries a per-call nonce and a hash of tool plus arguments; the approval returns that nonce and hash, and the tool executes only if they match (closes the dialog-to-execution gap). Fail closed: default deny on timeout (30 s), if the tray is not connected, or if the pipe has a foreign server. One tray instance only; concurrent prompts queue; a locked screen defers the prompt until unlock and then times out. Dangerous tools are classified by a deny-by-default attribute on each tool; a test fails when a tool lacks a classification. Stdio is unchanged. Tool output is marked untrusted (prompt injection from logs/build output).
- **Shared state (audit):** static per process: `EventSubscriptions` (by pid), `ErrorTools.Services`, localization stores, `TestHostTools.Plans`, `TestingState`, `ManagedProcessRegistry`, `LiveRuns`, `ControlSession.Server`, `TerminalSessionManager`/`SessionRegistry`. Shared by design, with a shared-vs-per-session table. Fixes: plan-then-confirm tokens bind to `McpServer.SessionId`; `ControlSession` holds a set of servers and broadcasts pause/close; `OnlySubscribedPid` documented process-wide.
- **Token and endpoint files:** MCP.Http generates them on first start if absent (user-only ACL); the service adopts and re-ACLs them. Unit 1 therefore works without the service.
- **Tray capabilities (user context):** `ServiceController` reads service state as a standard user; start/stop/install need admin, so they go through pinned UAC scripts. `GetExtendedTcpTable` gives the listener owner pid across sessions, then the exe path is checked. The tray reuses the `InstanceRegistry`/`VsInstanceRegistry` manifest format with a read-only reader (no deletion, unlike `ListRunning`). `ServerControl.StatePath` is user-writable, so the SYSTEM supervisor ignores `closing` from that file for restart decisions and uses its own child-exit and `/healthz` signals plus the drain command it issues itself.
- **Stdio coexistence:** both exes share `ServerControl.StatePath`, `TerminalRegistry`, manifests, `AIDEVHELPERS_CONTROL_STATE`; event buffers differ per process (documented). The supervisor treats `server_control_set closing` as intended (waits for `running`; no restart loop).
- **Client support (Spike B):** Claude Code, VS Code Copilot, Cursor: HTTP with headers; Visual Studio least certain; Claude Desktop stdio only (stdio exe or `mcp-remote`). HTTP stays opt-in per client until verified; existing stdio configs keep working untouched.

## Service and update design
- Install under `%ProgramFiles%\AiDevHelpers`, created with an admin-only ACL before copy; the install script refuses a pre-existing user-owned path. `scripts/service-*.ps1` carry committed SHA-256 pins with `-WritePin` (`gate-tpm.ps1` model); deliverables listed in the unit. Recovery actions (restart on failure) set at install. Bootstrap trust anchor stated: the release public key is committed in the repo and pinned in the install script; the binary hash comes from the signed manifest.
- Staging folder admin-only with no user-writable parent. The service copies a package to a SYSTEM-owned temp folder, then verifies and applies from that copy only (`FILE_SHARE_NONE`); reparse checks repeat at apply. `allowDevUpdatePackages` is machine-only config (HKLM or admin-ACL'd ProgramData) and honored only in debug builds.
- Signed manifest: monotonic version, `notAfter`, hashes of every file (not only the manifest); `manifest.json.sig` inside the package. Public-key list in the service for rotation/revocation. Size cap, HTTPS only, downgrade rejected.
- Drain on update: `server_control_set paused`, wait for in-flight calls, then `closing`.
- Tray and service ship in one signed package; apply renames locked files `.old-*`, cleaned on next start; tray shows "restart for update" when `/healthz` versions differ.
- **Port rules** (`PORTED.md`): record the VideoForensics commit SHA and divergences; list which files are ported (`UpdatePackageVerifier`, `Ed25519PackageSignatureVerifier`, `UpdateApplier`, `UpdatePathGuard`, `UpdateManifest`, `UpdatesFolderAcl`, stager) versus dropped (`MaintenanceUpdateDrain`, `StagedUpdateInstaller`, VideoForensics contract types, `DefaultKeepList`); a test pins verifier behavior. Check whether .NET 10 has Ed25519 before adding BouncyCastle.
- CI: pin actions by SHA, `contents: read`, never `pull_request_target`, no signing on fork PRs. Release/signing workflow is separate, tag-triggered, protected environment with required reviewers, ruleset restricting `v*` tag pushes, `UPDATE_SIGNING_KEY` as an environment secret (manual step for the user), `RestorePackagesWithLockFile` for new packages, no `obj/` upload, crash-dump upload glob limited. Extend the existing `ci.yml` for build/test; confirm WPF/ASP.NET projects build under its MSBuild.

## Rx and MVVM rules
- View models take `IScheduler`; tests use `TestScheduler`. Every stream is `Replay(1).RefCount()` (or equivalent) so a new subscriber gets the current value. UI updates use `ObserveOn(dispatcher)`. Disconnection is a state (`Connected/Disconnected/Reconnecting`), never `OnError`. Log tail uses `Buffer(250ms)` batching. All subscriptions disposed with the view model (a long-lived process: a disposal test per view-model family). One `IObservable<AppState>` snapshot per page where it simplifies binding.
- Interfaces for every Win32/OS edge: `ISessionLauncher`, `IServiceController`, `IElevator`, `IFileSystem`, `IClock`, tray icon. Fakes for CI (windows-latest has no session 0 or UAC).
